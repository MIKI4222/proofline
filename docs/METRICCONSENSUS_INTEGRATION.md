# MetricConsensus integration

## Scope and provenance
Proofline's Metrics workspace integrates the unchanged MetricConsensus source at https://github.com/MIKI4222/metric-consensus-genlayer (source audited at commit `d70b1d7d27db541f9f948b8df33eed617f18367c`). No Python contract, deployment or consensus logic was modified for this work. UI/domain patterns and validation were adapted from the owner's PULSE project. The MetricConsensus repository contains only a README and root `metric_consensus.py`; the docs/tests referenced in its README are not present there and could not be inspected.

## Contract surface
Constructor has no arguments. Schema exposes three writes:
- `register_metric(metric_name, description, category, data_type, expected_unit, extraction_instructions, source_urls, min_sources, max_sources, max_age_hours, max_deviation_bps, aggregation_method, outlier_policy, external_ref)`.
- `add_metric_source(metric_id, source_url, label)` and `verify_metric(metric_id)`, owner only.

Eight views: `get_metric_count()`, `get_metric(id)`, `get_metric_sources(id)`, `get_observation_count(id)`, `get_latest_observation(id)`, `get_observation(id, number)`, `get_observation_history(id)`, and `get_integration_status(id)`. The constructor and method signatures were read from the live schema. Detailed field shapes are validated by Zod in `src/metrics/contract.ts` and derived from contract source.

Metric definitions are immutable; sources are append-only; up to 50 observations are stored. Registration supports zero initial URLs, but the Proofline wizard deliberately requests 2–5 so a useful evidence base is prepared. Source count must be within configured maximum and verification requires the configured minimum. Age 0 means no freshness requirement. Deviation is 1–5000 basis points; aggregation is MEDIAN, MEAN, MIN or MAX; outlier policy FLAG or EXCLUDE. The contract supports DECIMAL or INTEGER, categories FINANCIAL, WEATHER, STATISTICAL, BLOCKCHAIN, INFRASTRUCTURE, PERFORMANCE, OTHER, and the units listed in the wizard. Currency conversion is not supported.

Result statuses are `CONSENSUS_REACHED`, `DISAGREEMENT`, `INSUFFICIENT_SOURCES`, `OUTLIERS_DETECTED`, `SOURCE_UNAVAILABLE`, `STALE_DATA`, `INCONCLUSIVE`. An agreed unsuccessful outcome can be stored without an accepted aggregate; a consensus failure may leave no observation. The contract deterministically checks extracted values, units, grounding, freshness, duplicates, outliers and aggregation, while validators independently retrieve and extract source data. Confidence is informational, not a calibrated probability of truth. Source relationships are not proof of common ownership or independence. Source URLs are not snapshots.

## Architecture and routes
- `src/metrics/config.ts` defines the owner-supplied deployment, separate from existing contracts.
- `src/metrics/contract.ts` provides validated reads and a 30-second cache, with inflight deduplication and invalidation. `catalog.tsx` loads at most 12 IDs per page with batches of 3. Totals, filtering and ownership metrics only cover records loaded, except the contract count. Failures are disclosed.
- `src/metrics/validation.ts` and `preflight.ts` validate inputs and verify the live method schema, current owner and applicable source/observation limits before estimate and again before signing.
- `src/chain.ts` and `src/state.tsx` reuse the shared wallet, transaction review, fee estimate, submit, pending-hash recovery and consensus/finalization tracking. A successful status alone is not treated as successful execution. No keys are requested or stored. A submitted hash is retained in localStorage; an uncertain outcome requires inspecting/resuming before retrying.
- `/metrics` explorer; `/metrics/mine` wallet-filtered loaded records; `/metrics/new` registration; `/metrics/:id` details; `/metrics/:id/sources` append sources; `/metrics/:id/verify` review; `/metrics/:id/history` history and side-by-side comparison; `/metrics/:id/observation/:number` report; `/metrics/methodology` explains constraints. Netlify's existing SPA fallback serves direct route refreshes.
- UI shows stored values and evidence; comparison is side-by-side without asserting a new consensus or inventing a numeric score. No interpolated chart or unsupported transaction hash is invented.

## Relationships
The optional on-chain `external_ref` may be set to `proofline:milestone:<id>` or `proofline:claim:<id>`; the UI links and filters by this user-supplied string. It is not a verified cross-contract relationship. Such references may be incomplete or stale after a contract redeploy. Filter results cover only loaded metrics. No result automatically changes a milestone or claim; a milestone still requires its own contract workflow.

## Fees and release-candidate limitations
The existing app estimates a fee for each write via `estimateTransactionFeesForWrite` and passes `distribution` and `feeValue` to `writeContract`. Users see the estimated fee deposit before wallet confirmation. Actual spend and refund can differ. The official v0.123 guidance recommends Transaction Kit and a fee profile from representative tests; neither is integrated in this preview. The currently available `@genlayer/transaction-kit@0.1.0-rc.2` package declares `genlayer-js@2.0.0-rc.1`, whereas Proofline pins rc.3; compatibility has not been established, so this work does not introduce an unverified second SDK. Per-click simulation may be slow or insufficient for costly branches. Browser wallets may require test GEN. Do not point this RC integration at ordinary Studionet before its upgrade. See https://docs.genlayer.com/developers/consensus-v06-migration and https://docs.genlayer.com/developers/decentralized-applications/fees-and-transaction-kit.

## Testing and remaining limits
40 automated Vitest tests passed across 6 test files. New tests use mocked RPC calls: adapter routing, malformed and unavailable responses, cache/deduplication, source validation, contract-aligned argument order, schema/owner/limits and fee routing. `npm run lint` is a TypeScript check; `npm run build` creates the Vite bundle. Historical README claims about prior contract tests are not new live proof. No wallet write, transaction fee estimate on a real wallet, real consensus, UI-to-chain registration, verification, or observation report was performed in this integration. The fresh deployment had zero metrics, so no live metric detail or result could be validated. This is a development preview, not production verification. Local browser checks covered the wizard validation and wallet gate, direct routes, and desktop/mobile layouts; they did not submit transactions. Visual/UI and workflow test coverage is partial; network resets, incompatible schema and rate limits are surfaced instead of replaced by mock live data.
